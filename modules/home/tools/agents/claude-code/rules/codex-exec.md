# Rule: Codex Execution

How to invoke Codex non-interactively (`/implement`, ad-hoc runs, subagents).

For direct calls always use `codex exec`. The interactive `codex` TUI and its `-a`/`--ask-for-approval` flag do not apply — `codex exec` rejects `-a` and is already non-interactive. Add `--skip-git-repo-check` when not inside a git repo, since `codex exec` otherwise refuses to run.

## Coding standards

Codex loads the coding standards on its own — no need to inject them into the task prompt.
`~/.codex/AGENTS.md`, which Codex reads on every invocation from any working directory, is generated by `modules/home/tools/agents/codex/` in the dotfiles repository.
It points Codex at the shared rules in `modules/home/tools/agents/rules/`, the same files Claude Code loads, so the coding standards have a single source of truth.

## Confirm Codex is ready first

Before a batch of Codex work — once, not per call — confirm Codex is installed and authenticated with `/codex:setup`. It runs the companion's `setup --json` and reports `ready` along with node and auth status, and does not need the sandbox (so it succeeds even where `codex sandbox` fails). If Codex isn't ready and can't be made ready, it is not a usable executor — the caller picks the fallback (e.g. `/implement` switches to a Claude subagent).

## Probe the sandbox first

The restrictive sandbox modes (`read-only`, `workspace-write`) and the companion path (`codex:rescue`) all use bubblewrap, which needs an unprivileged user namespace. Hardened containers block that syscall, so the sandbox dies before any command runs. Probe Codex's own sandbox:

```bash
codex sandbox -- true >/dev/null 2>&1   # exit 0 = sandbox works
```

## Entry point: codex:rescue by default

When the probe passes and you just need Codex to run one self-contained task without custom flags, default to `codex:rescue` — the companion path gives you the sandbox, the review gate, result handling, and session resume for free.

Drop to direct `codex exec` when any of these holds:
- the probe fails — rescue depends on the same bubblewrap, so it can't run;
- you need to control exec flags (a specific `-s` mode, `-C <dir>`, `--output-schema`, etc.);
- the work is orchestrated or parallel — e.g. `/implement` fanning out across worktrees, where the caller is already the orchestrator with its own review step and the single-shot rescue forwarder doesn't fit.

## Sandbox flag for direct codex exec

- Probe passed → `codex exec -s workspace-write "<task>"` (writes confined to the workspace, network off).
- Probe failed → `codex exec -s danger-full-access "<task>"` (no confinement).

Also use `-s danger-full-access` when the task legitimately needs to go beyond the sandbox (network access, writes outside the workspace). The probe detects a broken sandbox, not a task that needs more than the sandbox allows — that second case is a judgment call.

## Safety

`-s danger-full-access` runs Codex with no confinement — it can read and exfiltrate anything reachable, credentials included. Use it only when an outer boundary (an isolated container) contains the blast radius, or the work is trusted. Never use it to skip a sandbox that actually works — prefer the sandboxed path (rescue, or `-s workspace-write`) whenever the probe passes.
